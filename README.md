# C3RB3R(.L0CK3D) 勒索事后 btrfs 无密钥恢复 —— 实战记录与方法论

> 一台无快照、无备份的群晖 NAS（btrfs）遭 C3RB3R 家族勒索后的**四天数据恢复全过程**。
> 未付赎金、无攻击者私钥，纯靠 **btrfs 写时复制（CoW）物理反演** + **勒索尾记录结构解析** 找回数据。
> 本文记录所有有效手段、所有被否决方案及其否决依据。

---

## 一、这件事值得一看的理由

教科书式的结论是："没有密钥、没有备份的勒索加密 = 数据全灭。"
这个案例给出了**第三个答案**：在 **CoW 文件系统**上，勒索软件的"覆写"并不会真正消灭旧数据副本——只要旧 extent 尚未被回收，明文就还躺在盘上，且可以**不依赖任何密钥**重建出来。

本项目的价值不在"解密算法"（没有），而在**一整套可复现的判定与取证链路**：

| 关键能力 | 说明 |
|---|---|
| **可恢复性的先验判定** | 解析勒索尾记录 588B 结构，在动手前就能判定每个文件是"可反演"还是"密码学死路"，避免在 0x24 全加密文件上白耗算力（本项目据此提前终止了对 265+368 个文件的无效努力） |
| **无密钥重建** | 用 btrfs 旧 extent（generation < 攻击代）反演还原原始文件，SHA256 可校验 |
| **诚实的失败边界** | 明确记录哪些文件不可恢复、为什么，以及被否决的 8 类方案各自败在哪一步 |

## 三、核心方法论

### 3.1 勒索尾记录：588 字节的"自白书"

C3RB3R 在每个被加密文件尾部附加 588B 尾记录，`footer_probe.py` / `footer_scan.py` 实测确证其结构：

| 偏移 | 长度 | 含义 |
|---:|---:|---|
| 0 | 48 | AES-256-CBC 包裹的 `file-key(32) + nonce(8) + nonce(8)` |
| 48 | 520 | RSA-2048 公钥包裹区（**无私钥不可破**） |
| 572 | 2 | **mode**：`0x24` 全文件加密 / `0x25` 分段 / `0x26` 仅前 1MiB |
| 574 | 2 | crypto：`0x20` 真加密 / `0x21` 诱饵 |
| 580 | 8 | **原始文件大小**（校验还原正确性的黄金标准） |

> **一处需要说明的修正**：项目早期依据家族情报将算法记为 ChaCha8；后续通过尾记录结构实测（偏移 0 的 48B 包裹块）与全批次字段校验（451/451 通过）修正为 **AES-256-CBC**。仓库内早期文档仍保留 ChaCha8 表述，读者请以 `tools/footer_probe.py` 的实测口径为准。

**这个结构的实战意义**：mode 字段直接决定可恢复性。

- `0x24`（全文件加密）→ 磁盘上不存在完整明文，**终局不可恢复**
- `0x26`（仅前 1MiB 加密）→ 尾部是完好原文，且旧 extent 常保留头部明文 → **可 100% 重建**
- `0x25`（分段）→ 视旧 extent 覆盖情况而定

本项目实测 451 个加密文件，mode 分布 `0x24=265 / 0x25=113 / 0x26=73`；其中 **0x24 的数量与"无旧 extent 覆盖"的数量精确吻合（265 = 265）** ——这条交叉验证直接否决了"全盘魔数雕刻"路线：既然全加密文件在元数据层就找不到旧引用，指望在裸扇区里刨出明文同样没有根据。

### 3.2 主路线：btrfs CoW 反演

勒索软件"覆写"文件时，btrfs 因写时复制会**分配新 extent 写入密文，旧 extent（含明文）暂时保留、不立即回收**。攻击写入有统一代际特征：

```
NEWGEN = 4,450,000   # 攻击代：低于它且高于 2026 年原文块代的 extent 即攻击前原文
```

反演流程（`tools/restore.py`）：

1. `dump_ext.py <subvol>` 导出 extent 表；`inomap.py <subvol>` 导出 inode→路径/大小表
2. 对每个目标 inode，收集 `gen < NEWGEN` 的旧 extent
3. 按 `文件偏移 = extent 逻辑偏移 + 偏移差` 逐段拼接（extent 表第 2 列是 btrfs 逻辑地址，**必须经 chunk 表做 l2p 换算**，直接当物理地址 seek 会读到乱码——这是本项目踩过的坑）
4. 用尾记录里的原始大小 + SHA256 做闭环校验

### 3.3 增强路线：extent 拼接法

对"部分损坏"的文件（前段密文、后段明文混杂），额外利用**旧 extent 的剩余空间**（extent 总大小 > 文件占用部分时，尾部可能残留更早版本的数据），做多版本择优拼接。本项目用此法将一张 JPEG 修复至 **100% 无损**（2301×4095，零字节空洞，PIL 完整解码验证）。

> 但此法**不是万能的**：批量推广到另外 10 张同类照片时全部失败——零字节区落在旧 extent 的**有效数据区内部**（已被覆写），而非剩余空间。推广前应先跑 `tools/cov.py` 做覆盖率普查，别指望通吃。

### 3.4 四重验证判据（缺一不可）

```
魔数正确  +  容器结构自检通过  +  大小 == 尾记录原始大小  +  SHA256 一致
```

**"段级完整"不等于文件完好。** 本项目明确区分"通过验证的恢复"与"部分损坏归档"，后者单独存放、不混入交付目录。

## 六、被否决的方案（及否决依据）

把"试过什么、为什么不行"写清楚，和写清楚"什么行"同样重要：

| 方案 | 否决依据 |
|---|---|
| 内存提取会话密钥（网传思路） | 需勒索进程仍在运行；受害机已多次重启，且会话密钥每次运行随机、不可跨受害者复用（全盘 marker 一致=单次运行） |
| 全盘魔数雕刻 | 0x24 文件数 = 无旧 extent 文件数（265=265），元数据层已证无明文残留 |
| 头部重建（PDF/JPEG 结构修补） | Root/页面树恰落在被加密的前 1MiB，MuPDF 修复引擎解析密文时直接崩溃 |
| 熵值判据识别明文 | JPEG/RAR 本身即高熵，误判严重；改用实际解码（PIL `im.load()`）验证 |
| …（完整 8 项见 03 号文档） | |

## 七、复现前提

1. **源盘只读**：`losetup -r`，禁用 `balance / defrag / discard / repair / rw mount`。先取 SHA 基线。
2. **先取样再全量**：32 样本端到端跑通并验证，再铺开。
3. **产物三副本**：工作目录 → 异地备份 → 过程产物归档，**不轻删任何中间产物**（本项目两次因批量清理脚本误删完好文件，教训固化）。
4. **环境**：Alpine/任意 Linux + `btrfs-progs` + Python3；跳板与串口通道按你的环境替换。
