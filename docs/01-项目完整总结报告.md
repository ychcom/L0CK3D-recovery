## 一、整体恢复思路

### 1.1 案件背景（事实基线）

| 项 | 内容 |
|---|---|
| 受害对象 | 旧群晖 NAS，虚拟机 nas-vm-a，运行于 ESXi 192.0.2.10 |
| 数据盘 | 4TB pRDM 物理直通（NVMe-4TB NVMe），btrfs（md1.2 之上），label 2024.09.16 |
| 攻击 | 2026-10-28 起，C3RB3R 家族（后缀 `.L0CK3D`、每目录 read-me3.txt、赎金 0.085 BTC） |
| 加密方案 | 每文件独立 ChaCha8 密钥 + RSA-2048 公钥封装（密钥附文件尾 588B），无公开解密工具 |
| 灾前防护 | 无快照、无备份（攻击链先删快照、停备份，再加密） |
| 感染规模 | 清单口径 169,083 文件 / 837GB，感染 156,127（92.3%）；技术终局口径被加密 312,382 个 |

### 1.2 恢复目标与范围界定

- **总目标**：在不付赎金、不破坏现场的前提下，最大化找回业务与个人数据。
- **范围依据**：以用户勾选清单《被感染磁盘-目录清单-待勾选.xlsx》第 16 列为**唯一恢复范围依据**（先后 5 次调整：勾选目录 → homes+team-share 高价值 → homes+team-share 剩余 → Share → homes/userA 8 目录、homes/userB、Share/Vmware/docker）。
- **排除项**（用户明示）：read-me3.txt 勒索信、MP4 视频、安装类 exe、Thumbs.db；Docker 镜像层子卷（十六进制命名目录）整体跳过。

### 1.3 核心原则（决策依据）

1. **源盘零写入**：全程只读挂载（losetup -r）、SHA 基线复核；禁 balance/defrag/discard/repair/rw mount。
2. **无密钥路线为主**：内存取证窗口已随机关机关闭，会话密钥丢失 → 只能走 **btrfs CoW 物理反演**（旧 extent 里的明文残留）。
3. **验证先于宣称成功**：SHA256 + 容器魔数 + 结构自检 + 大小 == footer 原始大小，四重判据缺一不可；"段级完整"不等于文件完好。
4. **分轮小步推进**：先 32 样本端到端验证方法论，再按价值分批全量，每轮独立盘点、独立导出。
5. **产物三副本思维**：Restore 工作目录（D 盘）→ 异地备份（R 盘）→ 过程产物归档（vmout 归档），不轻删任何中间产物。

### 1.4 关键约束与假设前提

- **通道约束**：本机(192.0.2.68) → WinRM → jump-host-a(192.0.2.98) → 串口 4555（单客户端）→ QEMU Alpine VM（内存 ~1GB、无持久化）→ 源盘。所有重型计算须在 VM 内存可承受范围内（曾因 OOM 重构为分块流式读写）。
- **存储约束**：C 盘 64GB 禁写大文件；D 盘优先（~200GB）；Y 盘（\\backup-nas\share-a 838GB）次选；R 盘（jump-host-a 1TB 本地共享）备选。
- **技术假设**（均已实证）：btrfs CoW 使被替换的旧 extent 未立即回收；攻击写入代 NEWGEN=4,450,000（低于攻击代、高于 2026 年原文块代）；C3RB3R 尾记录 588B 结构固定。
- **已知不可行前提**：ESXi 层无任何残留副本（pRDM 不支持快照）；旧目录树元数据无一份"加密前"版本留存。

## 二、实现路径（分阶段）

```
阶段0 应急保护 → 阶段1 全盘盘点 → 阶段2 方法论验证
   → 阶段3-7 分轮批量恢复 → 阶段8 归位/备份/归档 → 阶段9 终局档案
```

### 阶段0：应急与鉴定（10-31）

- **关键动作**：勒索样本鉴定（确认 C3RB3R 新家族，非 2016 老 Cerber，严禁老解密器）；源盘 Windows 层设只读 + 前 1MB SHA 基线；ESXi 关 UNMAP/确认 pRDM 无块回收（属恢复前置动作，防块回收侵蚀旧 extent 残留）。
- **产出**：勒索恢复操作手册、样本鉴定结论、源盘只读基线。

### 阶段1：全盘盘点（10-31 ~ 11-01）

- **依赖**：阶段0 的只读通道。

### 阶段2：方法论验证（11-01，决定成败）

- **关键动作**：确认 C3RB3R **分段加密**规律（<1MB 全加密；1–5MB 只加密前 1MB；>5MB 加密 3 段×~4%）；发现 btrfs CoW 算术反演（PRE/POST 双锚点定位旧 extent 明文）；端到端还原 32 个有备份样本。
- **产出**：解锁验证报告 —— **≥1MB 文件 100% 逐字节还原（28/28），<1MB 全部失败**；restore.py 端到端还原器定型。

### 3.2 已确认有效的技术结论

1. **加密档位规律**（footer mode 字段实证）：0x24=全文件加密、0x25=分段、0x26=前1MiB；crypto 0x20=真加密/0x21=诱饵；尾部 588B 含 48B AES 包裹的 ChaCha8 密钥 + RSA-2048 区 + 原始大小。
2. **CoW 反演有效性**：≥1MB 的 0x25/0x26 文件可 100% 逐字节还原（多轮数万文件验证）；NEWGEN=4,450,000 阈值正确。
3. **extent 拼接法**（rebuild.py）：可修复"损坏区落在旧 extent 剩余空间"的文件（35.jpg 修复至 100% 无损）。
4. **结构自检判据**：魔数 + SOI/EOI 等结构 + 大小==orig + SHA256 四重验收；熵判据仅兜底（压缩流天然高熵会误报）。
5. **单一会话攻击**：451 个文件 marker 全部 = e3b6ccee（同一次运行）→ 会话密钥不可跨文件复用，也佐证内存提取路线与本案无关。

### 3.3 已被否决的方案（均有实证依据）

| 方案 | 否决依据 |
|---|---|
| ESXi 层副本（快照/delta/vmsn） | pRDM 物理直通不支持快照，三个 datastore 搜索无残留 |
| 攻击前目录树还原 | 存活旧树根全部在攻击开始之后，无一份加密前版本 |
| 纯魔数全盘雕刻 | 0x24 全加密 265 个与"无旧 extent 覆盖"精确吻合——磁盘上无明文；且回收文件名 |
| 52pojie 帖子解密思路 | 需加密进程仍在运行提取内存密钥；设备已重启，且会话密钥一次性 |
| JPEG 头部重建 | 无同步字 + DC 差分预测，不可行 |
| UFS Explorer 数据复制 | btrfs 支持只到元数据层，数据块读出 0KB |
| @eaDir 缩略图救援 | 7,426 个 100% 加密 |
| 付赎金 | 不建议（且不解决本次技术账目） |

## 四、风险与应对

### 4.1 主要风险点

| 风险 | 等级 | 应对 |
|---|---|---|
| 源盘被误写（NVMe TRIM/GC 持续侵蚀残留数据） | 高 | 只读挂载 + SHA 基线复核；VM 无持久化，每次重建环境仅 apk add；未跑任何修复类工具 |
| 大批量删除误伤完好文件 | 高（已发生2次） | 教训固化：任何清理先排除 final_verdict ok 清单；删除走回收站并确认释放；批量删除须用户授权 |
| D 盘空间耗尽导致流程中断 | 中 | 已建立 D→Y→R 存储优先级；大文件流式直传，VM 占用恒定 |
| restore.py 工程性缺陷（OOM/双实例/命名冲突/路径转义） | 中 | 已全部修复沉淀：分块读写、互斥锁、批次独立前缀、`\ ` 空格还原；新批次沿用即可 |
| 误判"乱码为成功" | 中（第5轮曾发生） | 三重甄别（魔数/熵/结构）已固化为导出判据 |
| 恢复现场断链（WinRM/串口/HTTP 服务） | 低 | 均可重建；8123/8124 用完即停（当前运行中，待确认） |

### 4.2 失败时的回滚与降级策略

- **文件级降级**：部分损坏文件（如 11 张毕业照片 0.4% 灰带）按"部分恢复"归位并标注，不因瑕疵弃整文件。
- **密码学不可恢复降级**：公开开源/可重下载内容用官方发行版替代归位（docker rar 已执行，明示"字节不一致、内容一致"）；密文完整留存 `_加密留存\`，万一日后拿到私钥可再解。
- **误删回滚**：以 vmout bin + final_verdict 为权威底账，任何误删可按 inode 重还原（49 个 Share 文件已验证此路径）。
- **整体回滚**：所有轮次产物保留独立 manifest（SHA256），导出脚本幂等（已存在且校验一致视为成功），可安全重跑。

### 4.3 验证与验收标准（固化口径）

1. 段级：restore manifest 标注 complete/置信度；
2. 容器级：魔数 + 结构自检（JPEG SOI/EOI、PDF %PDF/%%EOF、ZIP 完整性测试、RAR 头）；
3. 尺寸级：输出大小 == footer 记录的原始大小；
4. 内容级：有备份者 SHA256 全等；图片用 PIL 实际解码（强制完整解码防花屏）；
5. 账目级：Restore 目录实际落盘数与各轮清单交叉核对（曾借此发现 2,042 个乱码误判）。
