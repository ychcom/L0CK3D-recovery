# L0CK3D 勒索病毒感染机制分析与 FTP 冷备份防护评估

**日期**：2026-11-03
**依据**：本恢复项目四天取证实测（588B footer 解析 451+ 文件、子卷 256/257/259/260/261/262 全量盘点）× 公开安全情报交叉验证（Synology-SA-26:14、CVE-2026-13639/13684、360/安全团队逆向报告）

---

## 一、结论速览

1. L0CK3D（自称 C3RB3R）是**针对 Linux 服务器/NAS 的自动化勒索载荷**：拿到高权限后在本地从根目录多线程遍历**所有已挂载的可写存储**，逐文件混合加密。
2. **独立 FTP 文件服务器（存储不挂载到受害机上）本次不会被动感染**——该载荷不通过 FTP 协议传播；但 FTP 服务器若与受害 NAS 有存储级耦合（挂载/同一台机器/复用凭据）或自身暴露公网，仍会中招。
3. **冷备份能保住数据，但保不住服务**：它切断的是"本机备份一锅端"这条杀伤链；若入侵入口（未修补的公网暴露服务）不关闭，新 FTP 服务器上线后仍会被同一波自动化攻击再次攻陷。
4. 防护要点排序：**公网暴露面收缩 > 补丁 > 强凭据+MFA > 不可变快照 > 离线+异地备份（3-2-1）> 恢复演练**。

---

## 二、感染机制（实证 + 情报）

### 2.1 加密器行为（本盘实测确证）

| 项目 | 实测结果 |
|---|---|
| 家族标识 | 后缀 `.L0CK3D`，各目录投放 `read-me3.txt`（含 C3RB3R INSTRUCTIONS） |
| 运行方式 | 451+ 文件 marker 全部 = e3b6ccee → **单次运行、一次性扫盘**（无长期驻留加密） |
| 加密算法 | 每文件独立对称密钥（AES-256-CBC），密钥经内置 RSA 公钥包裹存于文件尾（footer 588B：0-48B 密钥包裹区 + 48-568B RSA 包裹区 + mode/crypto/原始大小字段）；公开报告另有 ChaCha/RSA-4096 说法，算法细节各家有分歧，**"无私钥不可解"是共识且与实测一致** |
| 加密策略（提速设计） | ≤1MiB 文件全加密（mode 0x24）；>1MiB 只加密头部/分段（0x26/0x25）——**为在最短时间窗口内覆盖最多文件** |
| 遍历范围 | 根目录起多线程巡检：子卷 256（顶层）、257（Share）、260（homes）、262（docker）等**全部用户子卷无一幸免** |
| 附带伤害 | 同机可写目录下的日/周/月备份、Hyper Backup 目标、Docker 卷内数据（本盘 dbwiki 即在 docker 子卷内）**全部按普通文件加密** |
| 诱饵机制 | footer 存在 crypto=0x21 诱饵位（部分样本为假加密），增加逆向干扰 |

### 2.2 入侵路径（公开情报；本机入口未定 → 待确认项）

本轮（2026-10 下旬）为**僵尸网络对暴露公网设备的全网自动化攻击**，非传统"Windows 中毒经 SMB 横向波及"。已知路径按可信度排列：

1. **DSM 原生套件 1day RCE**：CVE-2026-13639 / CVE-2026-13684（2026-09-18 官方已发补丁，受害设备多为未更新）；及 Synology-SA-26:14（PHP 核心 RCE，CVE-2026-109618/109619，影响 Calendar、MailStation、Web Station 等套件，无需账号密码）。
2. **Docker 容器路径**：Container Manager 里自建 GitLab / Confluence 等，端口映射公网，容器 RCE + 高权限挂载/宿主逃逸 → 恶意脚本写入 **crond 定时排程静默潜伏**。
3. **弱口令/凭据爆破**：对 5000/5001/22 等端口的字典攻击（历史上群晖官方证实过此类僵尸网络）。
4. **Confluence 漏洞横向**（CVE-2023-22518 等）：该家族 2023 年打 Windows/Linux 服务器的旧路径，内网存在未修补 Confluence 时仍可能触发。

**与本盘证据的契合**：该机为 DSM + btrfs 群晖架构、docker 子卷内跑过多种服务（obsidian、迅雷下载目录、GitLab 类软件包），且全部子卷一次扫盘加密——与"公网 RCE 拿到 root 后本地遍历"模式完全一致；无 SMB 横向感染的特征。具体入口（哪个服务/哪个 CVE）**无日志佐证，列为待确认项**。

## 三、FTP 文件服务器会不会被感染（分场景）

判定原则：**该载荷的杀伤半径 = 受害机 Linux 命名空间内所有可写挂载点**。它不实现 FTP 协议传播、也不主动爆破 FTP 服务。

| 场景 | 是否会被本次感染波及 | 机理 |
|---|---|---|
| FTP 服务就架设在受害 NAS 上（DSM 的 FTP 套件共享同一批目录） | **会，已证实** | 共享目录即被加密目录 |
| FTP 服务器是独立机器，但存储经 SMB/NFS/iSCSI **挂载到受害 NAS** | **会** | 载荷遍历 `/` 时会穿过挂载点继续加密 |
| 独立 FTP 服务器，与 NAS 无存储耦合，仅通过 FTP 协议互传 | **不会（本次）** | 载荷不说 FTP 协议，无网络文件遍历行为 |
| 独立 FTP 服务器暴露公网（尤其明文 FTP/弱口令/旧版 vsftpd 等） | **有独立风险** | 不属于本次攻击路径，但属于经典攻击面（爆破、匿名上传、漏洞利用） |
| 攻击者经后门二次入侵内网（webshell/后门账号/复用凭据） | **存在可能** | 情报明确存在"二次锁死"风险；人工横向阶段可打任何可写目标 |

> 关键结论：**"FTP 协议"本身不是传播通道；"可写挂载关系"和"自身暴露面"才是判据。**

## 四、冷备份（离线备份）重建 FTP 服务器的防护评估

### 4.1 能有效防范的场景

1. **加密杀伤链本体**：攻击运行时备份介质离线/断连，载荷遍历不到 → 数据不可达即不可加密。这正是本轮"日/周/月备份一锅端"的解药（受害者通病是备份写在同一台可写机器上）。
2. **二次锁死/持久化破坏**：攻击者植入的 webshell、crond 载荷只存在于受害主机；从干净冷备份重建的新服务器不含这些持久化组件。
3. **数据完整性兜底**：冷备份若在感染前取得并经验证（魔数 + SHA256），恢复出的文件可信——本项目 1,709 个完整可用恢复件采用的四重验证（魔数+结构+尺寸+SHA256）即此标准。
4. **恢复能力独立于赎金谈判**：该家族无公开解密工具，备份是唯一可靠恢复路径。

### 4.2 仍然存在的风险（冷备份管不到的）

1. **再次感染（最大风险）**：冷备份保护的是数据副本，不是服务本身。若新 FTP 服务器上线后仍然公网暴露、未修补、弱口令，同一僵尸网络的自动化扫描会再次光顾——本轮攻击是持续性的全网扫描，不是一次性事件。
2. **备份时点污染**：若冷备份是在感染**之后**取得（如 NAS 上先加密、后拷出），备份里就是密文。恢复前必须逐文件验证（本项目实测：`Rar!`/`PK`/`%PDF` 魔数 + 结构校验可 100% 区分密文与明文）。
3. **恢复内容带毒**：从受害盘恢复的可执行文件/脚本/压缩包可能含恶意载荷（本盘 docker、downloads 目录大量软件包曾被同波感染）。**数据文件可恢复归位，程序类文件应一律从官方渠道重新获取**（如本项目 obsidian 插件的处理方式）。
4. **"冷"不彻底**：介质只是"平时不插"但恢复期间长期在线挂载，或为图方便常驻挂载——一旦挂载即回到在线暴露状态。需要制度化的轮换离线。
5. **网络内残留威胁**：原受害机若未彻底处置（重装/隔离），webshell 与后门账号仍在内网存活，可通过 SMB/SSH 横向触达新服务器（含复用相同密码的情况）。
6. **FTP 服务自身攻击面**：明文 FTP 凭据可被嗅探、匿名/弱口令可被爆破、旧版服务软件有已知漏洞——这些与勒索无关，但同属数据安全风险。

### 4.3 结论

**冷备份 = 必要条件，不是充分条件。** 它把"数据全灭"降级为"服务中断 + 数据可恢复"；要避免"再次感染"，必须同时关闭入侵入口（见下节）。本次事件中本机 R 盘异地备份（robocopy + 全量 SHA256 校验、与 NAS 无挂载关系）未被波及，就是冷/异地备份有效性的实证。

## 五、防护建议（按优先级）

**第 1 层：消灭入口**
- DSM 及所有套件保持自动更新（本轮补丁 2026-09-18 即发布，受害者全是没更的）
- 取消端口转发/UPnP，DSM、FTP、SSH 不暴露公网；远程访问一律走 VPN
- Docker 容器（GitLab/Confluence 等）端口不映射公网，最小权限运行，及时更新镜像
- 禁用默认账号，管理员强口令 + 2FA，开启自动封锁与登录日志审计

**第 2 层：缩小杀伤半径**
- 共享权限最小化：归档目录只读、拆分大共享，避免"所有人可写"
- **开启 btrfs 不可变快照**（Snapshot Replication + WORM 保留，DSM 7.2+）：本次我们靠 CoW 旧 extent 反演救回 1,709 个完整可用文件（另有 2,738 个部分可恢复），本质是吃到了 CoW 快照式保护的"残羹"——主动快照 + 锁定远比事后反演可靠
- 关闭不需要的服务（Telnet/AFP/明文 FTP），FTP 必须 via VPN；如需对外用 FTPS/SFTP

**第 3 层：备份体系（3-2-1）**
- 3 份副本、2 种介质、1 份**离线+异地**；至少一份严格冷备份（断电/断连存放，制度化轮换）
- Hyper Backup 目标必须在 NAS 之外；同步类（Cloud Sync）配置单向且警惕反向投毒
- 每次备份后验证可恢复性（抽样魔数 + 哈希）；新架 FTP 服务器恢复前对冷备全量校验

**第 4 层：新 FTP 服务器上架专项**
- 操作系统/服务软件全新安装（不从受害盘恢复程序文件），数据经四重验证后导入
- 原 NAS 在取证完成前保持隔离，处置前假定其含 webshell/后门；内网凭据全部更换，不复用
- 上线后前两周加强监控（登录日志、crond 任务、异常文件改名 .L0CK3D 告警）

## 六、待确认项

1. 本机确切入侵入口（DSM 套件 1day / Docker 容器 / 弱口令）——需保留 read-me3.txt、SSH 登录记录、容器日志做取证，当前无日志佐证
2. 攻击者是否在本机留有 webshell/后门账号（决定原机处置方式与凭据更换范围）
3. 网内其他机器（jump-host-a 等）是否被横向触达过——目前无异常迹象，建议排查
4. 对称加密算法精确分支（AES-CBC / ChaCha 系）各家报告有分歧；不影响"无私钥不可解"的结论，仅影响日后若拿到私钥时的解密器编写
