## 二、技术终局分类判定

### A. Share 子卷 —— 物理层就地覆写，**技术不可恢复**

| 指标 | 数值 |
|---|---:|
| Share 被加密文件 | 65,080 |
| 已尝试反演 | 15,693 |
| 判定完好 | **49（0.31%）** |
| 判定乱码 | 15,644 |

**判定证据（关键）**

1. 第 5 轮 manifest 中 **15,501 / 15,693 条标记为 `NO_CIPHER`** —— 即反演路径上不存在密文段，
   按 btrfs CoW 反演原理，这类文件应还原出**原始明文**；
2. 但对还原产物做三重甄别后 **15,644 个被判为乱码**：
   ① 扩展名期望魔数不符；② 字节熵 ≈ 8.0（加密数据特征值）；③ 按类型复核（CAD 应为 AC10xx、
   MOV 应为 ftyp、PSD 应为 8BPS 等）全部不通过；
3. 元数据层佐证：btrfs 树中这些文件的 extent 条目**仍是旧 generation、无新 extent 产生、
   无 CoW 旧副本**。

**机理**：勒索软件对 Share 子卷采用**就地写入（in-place write）**——不触发 CoW 分配新块，
而是直接把密文写回原物理块。因此元数据树中的引用依旧指向原逻辑块、generation 未更新，
反演"成功"地读回了该物理块，但块内早已是密文。

**结论**：源的物理字节已被覆盖，任何基于本磁盘的手段（CoW 反演、元数据回退、块级扫描）
均无法还原明文。**唯一出路是找到独立副本**（异地备份、云端、他人持有的拷贝）。

### B. NO_ANCHOR 10,336 个 —— 元数据无引用，理论可试旧 generation leaf 扫描

**判定**：文件 inode 在现行元数据树中找不到有效的 extent 锚点（多为小于 1MB 的小文件，
文件体可能内联在 metadata 中或已被回收）。

**理论方案**

1. 全盘顺序扫描物理块，按 btrfs metadata 特征（`_BHRfS_M` magic + 校验和）识别 metadata 块；
2. 解析 leaf node 中的 `EXTENT_DATA` 项，按 `inode + offset` 重建旧版 extent 映射；
3. 对重建出的旧映射回读物理块，按 generation 取最旧可用版本；
4. 用小文件（<1MB，可能内联）优先验证。

**可行性评估**

| 维度 | 评估 |
|---|---|
| 数据基础 | 已具备：`_audit/ext257.tsv`（57,227 条 extent，覆盖 499.95 GB）、`ino257/260/261.tsv` |
| 成功窗口 | 取决于旧 leaf 块是否尚未被重新分配。btrfs 释放块进入 free space 后内容通常保留到被覆写为止，存在窗口期 |
| 工作量 | 需 dump 全盘 metadata 区（数 GB 级）并解析匹配，预计**数小时至数十小时** |
| 成功率 | **未知，保守估计偏低**（NO_ANCHOR 本身即意味着树中已无引用，需要依赖残留旧块） |
| 建议 | 仅在锁定明确高价值目标后针对性尝试，不宜全量投入 |
