# homes/userA/Photo 加密规律分析与还原结论

> 范围：清单中你已勾选为「需要恢复」的 3 个目录 —— `homes/userA/Photo/2015`、`2018`、`2019`
> 备份源：`D:\backup-preinfection`
> 方式：**全程只读**（仅 `btrfs inspect-internal dump-tree` + 按物理偏移读取），未写入/移动/修改源盘任何数据，未执行任何被感染文件。

## 一、明确结论

### ❌ 不能通过明密文对比推算出解锁方式（密钥不可反推）

理由一句话：**这是真随机流密码 + 每文件独立密钥**，明文-密文对再多也无法反推，因为密钥不在密文里、也不在别的密文里，而是被一个只在内存中存在过的全局密钥加密后写进了每个文件的尾部。

### ✅ 但有一个此前被误判的关键事实：这是「间歇加密」，未加密部分完好保留原文

C3RB3R **并没有加密整个文件**。实测证实：

- **未加密区段的字节 = 加密前的原始明文**，逐字节相同率 **1.000000**（s17 47/47、s19 56/56、s20 56/56 个探测点全部完全一致）
- 对 `>1MB` 的文件，盘上保留了 **57%~87.5%** 的原始明文

> ⚠️ 更正：此前项目里记录的「全文件加密、1MB 之后完好」**两个说法都不准确**。前者源于旧版提取器把 btrfs extent 的**总长度**误当作 item 覆盖长度，导致读取错位；后者是同一次误判的另一面。本次已修正提取器（`dl/fetch5.py`），extent 区间现已严丝合缝、无重叠，以下结论以修正后数据为准。

## 三、加密规律（7 项实测证据）

### 1. 文件名：不混淆
原名 + `.L0CK3D`，原名未被改写。实测 20/20 全部为「原名 + .L0CK3D」。

### 2. 体积：恒 +588 字节
308/320 = **96.25%** 的配对体积差恰为 **+588**。

### 3. 尾记录 588 字节结构

```
[0   .. 299 ]  300B 随机段   ← 前 48B 为被全局 AES-256 加密的「每文件 ChaCha8 密钥+nonce」
[300 .. 571 ]  264B 全零填充
[572 .. 587 ]  16B marker
```

### 4. marker 字段（可直接读出原件真实大小）

```
marker = [ 档位常量, 240002, 原始文件大小, 0 ]      ← 26/26 个样本全部命中
```

第三个 u32 **恒等于「密文大小 − 588」**。这条极有价值：**只要能读到文件尾部，就能知道加密前原件的真实大小**，可用来验证任何候选还原方案是否正确。

### 5. 档位常量（本次新发现，与加密模式严格对应）

| 常量 | 十六进制 | 适用 | 加密行为 |
|---|---|---|---|
| 2097188 | `0x200024` | 小文件 **<1MB** | 整文件加密，无残留 |
| 2097190 | `0x200026` | 中文件 **1–5MB** | 加密**前 1MB**，其后 57%~73% 为明文 |
| 2099749 | `0x201E25` | 大文件 **>5MB** | 加密 **3 段**，每段约 4%，起点约 0% / 48% / 96%，明文残留 87.5% |

### 6. 加密区段实测图（64 点密集探测，`#`=密文 `O`=明文）

```
s14 IMG_20180603_155104.jpg (2.6MB)  ##########################OOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOO#
s15 IMG_20180626_151201.jpg (3.0MB)  ######################OOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOO#
s17 IMG_20180628_064300.jpg (4.3MB)  ################OOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOOO#
s18 IMG_20181005_095623.jpg (5.4MB)  ###OOOOOOOOOOOOOOOOOOOOOOOOOOOO##OOOOOOOOOOOOOOOOOOOOOOOOOOOO##o
s19 VID_20190116_205328.mp4 (296MB)  ###OOOOOOOOOOOOOOOOOOOOOOOOOOOO##OOOOOOOOOOOOOOOOOOOOOOOOOOOO###
s20 VID_20180314_221925.mp4 (134MB)  ###OOOOOOOOOOOOOOOOOOOOOOOOOOOO##OOOOOOOOOOOOOOOOOOOOOOOOOOOO###
```

**共同点：文件最开头（0% 位置）一定被加密** —— 这正好毁掉 JPEG 的 `FFD8FFE1` 头/EXIF 和 MP4 的 `ftyp`/`moov`，所以文件无法直接打开。

### 7. 未加密区段 = 原始明文（100% 一致）

| 样本 | 达到 >99% 相同的探测点 | 其中**完全一致** |
|---|---:|---:|
| s17 (4.3MB) | 47 | **47 / 47** |

## 四、为什么反推不出密钥（4 项密码学判定）

| 检验 | 结果 | 判定 |
|---|---|---|
| XOR 密钥流熵 | 7.972 – 7.981（上限 8.0） | **真随机流密码**，排除固定异或/固定偏移/字节重排 |
| 跨文件密钥流复用（20 样本两两比对） | 最大相同率 **0.5859%**（随机期望 0.39%） | **每文件独立密钥**，不可复用 |
| 周期性自相关（P=16/64/256/1024/4096） | 0.39% – 0.44%，全为随机水平 | **无周期**，非定长重复密钥 |
| 明密文相同率 | 0.3% – 0.5% | **无明文残留**，不是「只改头尾」的伪加密 |

**密钥体系**：

```
全局 AES-256 会话密钥（48B = IV 16B + KEY 32B）  ← 只存在于加密进程内存，旧 NAS 已关机 ⇒ 已消失
        │  加密
        ▼
每文件 ChaCha8 密钥 + nonce  →  写入该文件尾记录前 48B
        │
        ▼
文件数据（间歇区段）被 ChaCha8 流密码加密
```

RSA-2048 私钥在攻击者手中。AES-256 与 ChaCha8 本身均不可攻破。

## 五、还原路径

### ✅ 路径 1：用备份直接还原（308 个，无需解密）

这 308 个文件的 `D:\backup-preinfection` 备份**就是原件本身**（体积差恒为 +588，且尾部 marker 记录的原件大小与备份大小完全一致）。

```

严格保留目录层级与文件名
```

### ⚠️ 路径 2：头部重建（有条件，待验证）

对 1–5MB 档的文件，盘上保留其后 57%~73% 的原文。若能取得**同一相机、同一设置**的 JPEG 头部（可从备份中同批次照片取得），理论上可拼接：

```
[备份照片的 SOI+APP1+DQT+DHT+SOF0 头] + [盘上未加密区段的扫描数据]
```

结果：文件可打开，但图像上半部分损坏（1MB 之后的扫描数据缺少前序 DC 预测值，需靠 RSTn 重启标记对齐）。**成功率不确定，需先拿 2–3 个样本验证。**

### ❌ 路径 3：推算密钥 —— 不可行
见第四节。

### ❌ 路径 4：内存取证 —— 该路已关闭
专业机构（GitHub `c3rb3r-rescue` 等）成功案例的本质是**抢在密钥消失前从进程内存里捞出 48B 全局密钥材料**，其文档明确写着「已关机或重启 → 不能靠重新启动找回之前的进程内存」。旧 NAS 已关机，不适用。

## 七、12 个「体积差 ≠ 588」的定性

这 12 个不是加密规律不同，而是**备份与 NAS 原件是同一张照片的不同编码版本**：

- EXIF 拍摄时间与文件名完全吻合（如 `IMG_20180926_090016.jpg` → `2018:09:26 09:00:11`），确认是同一张照片
- 但尾部 marker 记录的**原件大小 ≠ 备份大小**（如备份 8,216,425 B，NAS 原件 1,306,940 B）

说明备份是高码率原图，NAS 上存的是压缩版本。用备份替代会**改变内容**（质量更高，但与原文件不是同一份字节），是否替替代由你决定。
