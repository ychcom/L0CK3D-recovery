### 明确否决（不要再投入）

| 路线 | 裁定 | 量化理由 |
|---|:--:|---|
| 由明密文对反推密钥 | ❌ | ChaCha8 至今无单密钥攻击；最好结果（7轮）需 2^126 个块，我们每密钥只有 2^14 个，**差 2^112 倍**。308 组明文不降低难度——每文件是独立密钥，是"308 个独立小问题"而非"一个问题的 308 倍数据" |
| nonce 复用 / XOR 消去 | ❌ | 跨文件密钥流最大相同率 0.5859%（多重检验校正后不显著）；XOR 最长零游程 = 2 字节 = 随机水平。且"同密钥不同 nonce"本就不可利用 |
| 尾记录 ECB 关联攻击 | ❌ | `[0,304)` 内 494 个 16B 块跨文件**重复组 = 0**；两两相同率 0.4049% ≈ 随机 |
| `.vswp` / swap 找会话密钥 | ❌ | power-off 时已删；受害者信任域内**从无私钥**（RSA 公钥封装）；流密码无 key schedule，扫到 32 字节无法自证 |
| vmkernel core dump | ❌ | 装的是 vmkernel 自身内存，**不含 guest 用户态内存**（常见误解） |
| CBT / `*.ctk` | ❌ | pRDM 结构性不支持 Changed Block Tracking |
| pRDM 快照链 | ❌ | `vmfsPassthroughRawDeviceMap` + 无 `parentFileNameHint` |
| JPEG 头部重建 | ❌ | 熵编码无同步字，无法定位 MCU 边界；DC 系数跨 MCU 差分预测，缺前段后永久色偏并向下传播。除非原图带 DRI/RSTn（`FFDD`） |
| PNG / DWG / SQLite 重建 | ❌ | deflate 必须从头解；DWG section locator 在头部；SQLite 页头毁 |
| `@eaDir` 缩略图 | ❌ | 实测 `SYNOFILE_THUMB_*` 7,426 个 **100% 加密**且均 <1MB；`SYNOPHOTO_*` 全卷 0 命中（未装 Synology Photos） |
| Cloud Sync 版本历史 | ❌ | 该机未安装 Cloud Sync |
| 付赎金 | ❌ | 0.085 BTC 且 5 天翻倍；无履约保障；警惕"包解密"中介二次收割 |

## 四、关键分歧与裁决

### 分歧 1（决定性）：CoW 旧块上的原文还在吗？

| 视角 | 判断 | 理由 |
|---|---|---|
| 存储 | **在**，90–95% | extent **未被拆分** → 被丢弃段仍是 allocated → 从未进空闲池 → 不可能被复用 |
| 密码学 | 可能在，50–70% | 需先验 TRIM |
| 取证 | 概率低，15–35% | btrfs 分配器倾向复用刚释放的 cluster |

**裁决：采纳存储视角的论证，并已用现网数据完成离线验算。**

铁证（`smp5/extents.tsv`，s18，整份原文件 = 单个 extent `345740496896`，`extlen=5,386,240`）：

```
[0,       217088)   密文   ← 被丢弃
[217088,  2580480)  明文   diskbyte=345740496896 dataoff=217088 itemlen=2363392 gen=222778
[2580480, 2801664)  密文   ← 被丢弃
[2801664, 5165056)  明文   diskbyte=345740496896 dataoff=2801664 itemlen=2363392 gen=222778
[5165056, 5386240)  密文   ← 被丢弃
        217088+2363392+221184+2363392+221184 = 5,386,240  ← 严丝合缝铺满 extlen
```

活引用与丢弃区间的 `dataoff/len` 正好铺满整个 `extlen` —— **extent 未拆分的铁证**。s19 / s25 / s26 同样成立（同一 `disk_bytenr` 上两个活引用，`dataoff≠0`，差值恰等于被丢弃段长度）。

若 btrfs 拆分了 extent，两个活引用会落在不同子 extent 上，`disk_bytenr` 不可能相同且 `dataoff≠0`。

**推论链**：未拆分 → 仍在 EXTENT_TREE 中 allocated（计入 bytes_used）→ 从未进空闲池 → 分配器不可能分给任何人 → **原始明文字节必定原封不动**。

这也顺带**修正了此前的悲观结论**：空闲只剩 13.25 GB 不是因为"被密文覆盖"，恰恰是因为被丢弃的段**没被释放**。

### 分歧 2：可救的未加密文件数

| 说法 | 数值 |
|---|---|
| 项目旧记录 | 71,392 个（其中 61,558 文档） |
| **取证视角复核** | **约 4,000 个 / 1–2 GB** |

**裁决：采纳复核值。** 旧数字未去重（`t*.tsv` 每条文件被 DIR_ITEM 与 INODE_REF 各记一次，正好 2 倍），且未剔除 `read-me3.txt` 勒索信与 `@eaDir`。剔除后真实未加密有效文件约 12,999 个 / 44.31 GB，其中 `.exe`(792/32.6GB) `.dll`(6,811/7.9GB) `.msi`(178) `.sys`(22) 全是可重装内容，占去约 44 GB。**不要按 71k 规划资源。**

### 分歧 3：尾记录结构

| 说法 | 结构 |
|---|---|
| 项目旧记录 | 300B 随机 + 264B 零 + **16B** marker = `[档位, 240002, 原始大小, 0]` |
| **密码学视角复核** | 48B AES块 + 256B RSA块 + 264B 零（`[304,568)` 26/26 全零）+ **20B** marker = `[magic=0xEECCB6E3, 档位, 240002, u64 原始大小]` |

**裁决：采纳复核值**（新增 magic `0xEECCB6E3`，26/26 恒定）。两者对"原始大小可从尾部读出"的结论一致，**不影响任何恢复方案**。另：`[0,48)` 熵偏低是采样量不足，非结构缺陷，无攻击面。

## 五、S1 方案详解（最高优先级）

### 原理（三句话）

1. CoW 粒度是 extent 不是文件。勒索软件只 `pwrite` 了加密段，未写区间**连动都没动**，仍指向原 extent 的原偏移。
2. btrfs 丢弃部分引用时**没拆 extent**，被丢弃段仍 allocated → 不会进空闲池 → **原文还在原处**。
3. 因此加密段的原始逻辑地址可**纯算术算出**，并双向校验。

### 定位公式

```
P_pre  = 前一个旧 item 的 diskbyte + dataoff + itemlen      （正推）
P_post = 后一个旧 item 的 diskbyte + dataoff − L            （反推）
P_pre == P_post  ⇒ 高置信；只有一个 ⇒ 单锚点；都没有 ⇒ 无锚点（<1MB 全加密）
```
